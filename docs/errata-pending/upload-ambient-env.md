### `dist/upload.sh` silently authenticated to Tigris as the owner's unrelated AMAZON keys (ticket #248)

#### The incidents

Two publishes, two days apart (s15 and s16), each failed with `InvalidAccessKeyId` from Tigris
partway through the multipart upload. `dist/upload.sh` (generated by `Tools/publish_cities.py`)
relied on `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` being exported in the ambient shell. Those
exports die with the terminal they were set in; on the next publish, with neither variable set,
the AWS CLI silently fell back to `~/.aws/credentials [default]` — the owner's own AMAZON keys,
unrelated to the `cypress-cities` Tigris bucket — and Tigris rejected them mid-upload with an
S3-internals error (`InvalidAccessKeyId`) rather than failing before any bytes moved.

#### The fix

`dist/upload.sh` now authenticates via a NAMED AWS CLI PROFILE
(`--profile "${CYPRESS_TIGRIS_PROFILE:-cypress-tigris}"`) on every `aws` invocation instead of
ambient environment. An explicit `--profile` makes the CLI resolve credentials from that profile
alone; it does not consult `AWS_*` env vars or `[default]`, so there is no environment left to be
hijacked by. Before any upload the script preflights the profile with a cheap authenticated call
(`aws s3 ls "$BUCKET" --endpoint-url "$ENDPOINT" --profile "$PROFILE"`, capped with
`--cli-connect-timeout`/`--cli-read-timeout`) and, on failure, exits immediately naming the fix:
`aws configure --profile cypress-tigris` (keys from the Tigris dashboard; see
`server/README.md`). The failure message distinguishes a missing profile (AWS CLI's own "config
profile ... could not be found") from one whose stored keys are stale or wrong for Tigris, where
the CLI's own error lets the two be told apart.

Everything else in the generated script is unchanged: same upload set, same `--content-type
application/json` on the manifest, same anonymous-GET verification tail (GET not HEAD, one-byte
ranges, `cmp` against `manifest.json`).

`Tools/publish_cities.py`'s UPLOAD docstring section and `server/README.md` were updated so
neither still teaches export-into-shell as the primary flow; the profile is primary,
`CYPRESS_TIGRIS_PROFILE` is the escape hatch for a differently named profile.

Cited by ticket #248, not by this filename.
