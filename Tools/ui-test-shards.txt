# Which XCUITest classes run on which CI runner.
#
# One shard per non-comment line; class names separated by spaces. `.github/workflows/testflight.yml`
# reads line N for matrix entry N and turns it into `-only-testing:CypressUITests/<Class>` arguments.
#
# WHY THIS FILE EXISTS RATHER THAN A LIST IN THE YAML. `UITestShardCoverageTests` reads it and fails
# the unit suite if any class in CypressUITests/ is missing from it, named twice, or named here but
# nonexistent. A shard list that can drift is a false green waiting to happen: a UI test class that
# belongs to no shard never runs, and CI stays green while it does not. That failure has to be
# impossible to reach by forgetting, so the check lives in a test rather than in a habit.
#
# ADDING A UI TEST CLASS: put it on whichever line is shortest. The unit suite will tell you if you
# forget; it will not tell you if you unbalance it.
#

# THE PLACEMENT DID NOT CHANGE, and this is the arithmetic that says it should not. Shard totals
# from the table above, with the class where it already sits:
#
#   Shard 1  314.8 + 17.8 + ~0                          = 332.6s
#   Shard 2  272.2 + 26.3 + 18.4 (+ 33.2 off-CI)        = 316.9s   (350.1s counting PhotoBrowser)

# Moving it does not help: Shard 1 becomes 332.6 + 35.6 = 368.2s, Shard 2 becomes 350.1 + 35.6
# = 385.7s, and Shard 3 becomes 344.8 + 35.6 = 380.4s — all worse than 362.6s. The four shards sit
# within ~30s of one another and this class now costs more than that spread, so wherever it goes it
# sets the pace; Shard 4 is the arrangement where it sets the pace lowest. The gate's longest TESTS
# therefore move 344.8s → 362.6s, +17.8s, on a pipeline whose per-shard BUILD is ~10 minutes — this
# file's own "diminishing returns" paragraph, which is why the answer here is arithmetic and not a
# fifth shard.
#
# THE WINNING MARGIN IS INSIDE THE NOISE, AND THE CONCLUSION SURVIVES IT ANYWAY (PR #54 review, N7).
# Best (Shard 4, 362.6s) beats second best (Shard 1, 368.2s) by 5.6s, and those two totals are not
# built from measurements taken on one machine: the table above is a CI iPhone 17 Pro, PhotoBrowser's
# 33.2s is a local 16 Plus, and this class's 35.6s is a local 16e. 5.6s is well inside that spread,
# so the Shard 4 / Shard 1 ordering must NOT be read as measured — it is a coin flip on this
# evidence. What IS robust is what the placement turns on: Shards 2 and 3 cost ~18-23s more than
# either, and no arrangement stops this class setting the pace, because it now costs more than the
# whole spread between shards. Either of the top two is right and the class is already on one of
# them. Re-measure on a single machine before moving it for a number this small.
#
# THE FLOOR WAS ONE CLASS, AND #204 MOVED IT. `DeepLinkVoiceOverTests` was 462.8s — 35% of the
# suite — because two of its 28 tests SWEEP every deep-linked screen, launching once per screen,
# where the other 26 examine one screen each. Those two are now `DeepLinkSweepTests`, which is a
# class the shard file and the compiler both understand. The alternative was a per-method shard
# list, and a list of method names is a list a rename breaks while `UITestShardCoverageTests` can
# only guard what the file names.
#
# DIMINISHING RETURNS ARE NOW REAL, and the honest number is small: the longest shard's TESTS drop
# from 462.8s to ~345s, about two minutes, on a pipeline whose per-shard BUILD is ~10 minutes.
# Sharding further would trade complexity for seconds. The next lever is the build each shard
# repeats, not the tests it runs.
